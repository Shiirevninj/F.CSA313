## 1. Зорилго

Энэхүү лабораторийн ажлын зорилго нь Mockito ашиглан програмын гадаад хамаарлуудыг mock объектоор орлуулж, бизнес логикийг тусгаарлагдсан орчинд нэгжийн түвшинд тестлэхэд оршино.

## 3. Тестлэгдэж буй систем

`CourseRegistrationService` класс нь оюутныг хичээлд бүртгэх бизнес логикийг хэрэгжүүлдэг.

Уг класс нь дараах хоёр хамааралтай.

- `StudentRepository` — оюутны мэдээлэл, хичээл болон өмнөх холбоо хичээлийг шалгаж, бүртгэлийг хадгална.
- `EmailSender` — амжилттай бүртгүүлсэн оюутанд мэдэгдэл илгээнэ.

Эдгээр интерфейст бодит хэрэгжүүлэлт ашиглаагүй бөгөөд Mockito-ийн `@Mock` annotation-оор орлуулсан.

`@ExtendWith(MockitoExtension.class)` ашиглан Mockito-г JUnit 5-тай холбож, `@BeforeEach` ашиглан тест бүрийн өмнө `CourseRegistrationService` объектыг шинээр үүсгэсэн.

## 4. Хэсэг A — Mockito нэгжийн тестүүд

Нийт A1–A8 гэсэн найман төрлийн тест боловсруулсан. A8 нь гурван өгөгдөлтэй параметржүүлсэн тест тул нийт 10 тест ажилласан.

| №  | Тестийн зорилго                   | Ашигласан арга                     | Үр дүн        |
| -- | --------------------------------- | ---------------------------------- | ------------- |
| A1 | Идэвхтэй оюутны амжилттай бүртгэл | `when`, `thenReturn`, `verify`     | Амжилттай     |
| A2 | Байхгүй оюутны бүртгэл            | `when`, `never`                    | Амжилттай     |
| A3 | Идэвхгүй оюутны бүртгэл           | `verifyNoInteractions`             | Амжилттай     |
| A4 | Өмнөх холбоо хичээл дутуу байх    | `when`, `never`                    | Амжилттай     |
| A5 | И-мэйл илгээх үед алдаа гарах     | `doThrow`, `verify`                | Амжилттай     |
| A6 | Null аргумент дамжуулах           | `assertThrows`                     | Амжилттай     |
| A7 | И-мэйлийн агуулгыг шалгах         | `ArgumentCaptor`                   | Амжилттай     |
| A8 | Гурван төрлийн алдааг шалгах      | `@ParameterizedTest`, `@CsvSource` | 3/3 амжилттай |

### Тестийн аргуудын тайлбар

`when().thenReturn()` ашиглан repository-оос буцах өгөгдлийг урьдчилан тохируулсан.

`verify()` ашиглан бүртгэл хадгалах болон и-мэйл илгээх үйлдэл дуудагдсан эсэхийг шалгасан. `never()` болон `verifyNoInteractions()` ашиглан алдаатай бүртгэлийн үед шаардлагагүй үйлдэл хийгдээгүйг баталгаажуулсан.

`doThrow()` ашиглан и-мэйл илгээх үед алдаа гарч буй нөхцөлийг дуурайлгасан. `ArgumentCaptor` ашиглан илгээгдсэн и-мэйлийн үндсэн агуулгад хичээлийн код орсон эсэхийг шалгасан.

### lenient() ашигласан эсэх

A8 параметржүүлсэн тестэд нөхцөл бүрд зөвхөн тухайн нөхцөлд шаардлагатай stub-ийг үүсгэсэн. Иймээс ашиглагдаагүй stub үүсээгүй бөгөөд Mockito-ийн strict stubbing алдаа гараагүй тул `lenient()` ашиглах шаардлагагүй байсан.

## 6. Хэсэг B — Мутацийн тест

Нэгжийн тестүүд кодын өөрчлөлт болон алдааг илрүүлж чадаж байгаа эсэхийг шалгах зорилгоор `CourseRegistrationService.java` файлын бизнес логикт гурван төрлийн зориудын өөрчлөлт хийсэн.

Мутаци бүрийн дараа `mvn test` ажиллуулж, үр дүнг тусдаа файлд хадгалсан.

| Мутаци | Хийгдсэн өөрчлөлт                        | Унасан тестүүд                                                                                                                        | Failures | Үр дүн        |
| ------ | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | -------: | ------------- |
| M1     | Идэвхгүй оюутны шалгалтыг арилгасан      | `inactiveStudent_whenRegistering_returnsError`, `invalidRegistration_whenDifferentConditions_returnsExpectedError(String, String)[2]` |        2 | BUILD FAILURE |
| M2     | `saveRegistration()` дуудалтыг арилгасан | `activeStudent_whenValid_returnsOK`, `emailFailure_whenRegistering_stillReturnsOK`                                                    |        2 | BUILD FAILURE |
| M3     | `courseId == null` шалгалтыг арилгасан   | `nullInput_whenRegistering_throwsException`                                                                                           |        1 | BUILD FAILURE |

### Мутаци №1

Идэвхгүй оюутныг бүртгэхээс хамгаалсан шалгалтыг түр арилгасан.

Үүний үр дүнд хоёр тест унасан. Энэ нь тестүүд идэвхгүй оюутны бүртгэлийг зөв хориглож байгаа эсэхийг шалгаж чаддаг болохыг харуулсан.

**Нотолгоо:** `results/mvn-test-mutant-1.txt`

### Мутаци №2

`repository.saveRegistration(studentId, courseId)` дуудалтыг түр идэвхгүй болгосон.

Үүний үр дүнд хоёр тест унасан. Энэ нь амжилттай бүртгэлийн үед өгөгдөл хадгалах үйлдэл заавал хийгдэх ёстойг тестүүд шалгаж байгааг харуулсан.

**Нотолгоо:** `results/mvn-test-mutant-2.txt`

### Мутаци №3

`register()` методын `courseId == null` шалгалтыг түр арилгасан.

Үүний үр дүнд `nullInput_whenRegistering_throwsException` тест унасан. A6 тест нь `studentId` болон `courseId` аргумент тус бүрийн null утгыг шалгадаг байсан тул уг өөрчлөлтийг илрүүлсэн.

**Нотолгоо:** `results/mvn-test-mutant-3.txt`

### Мутацийн үр дүнгийн нэгтгэл

Гурван мутаци тус бүр дор хаяж нэг тестийг унагасан бөгөөд бүгд `BUILD FAILURE` үр дүнтэй гарсан.

Мутаци бүрийн дараа үндсэн кодыг сэргээсэн. Эцэст нь 10 тестийг дахин ажиллуулахад `BUILD SUCCESS` гарсан.

Ингэснээр сонгосон гурван мутацийг тестүүд бүгд илрүүлж чадсан. Гэхдээ энэ нь програмын бүх боломжит алдааг илрүүлнэ гэсэн баталгаа биш юм.

## 7. Дүгнэлт

Энэхүү лабораторийн ажлаар Mockito ашиглан өгөгдлийн сан болон и-мэйл илгээгчийн хамаарлыг орлуулж, `CourseRegistrationService` классын бизнес логикийг тусгаарлагдсан орчинд тестэлж сурлаа. Mock объект нь методын буцаах утгыг тохируулах, дуудалтыг шалгах боломж олгодог бол гараар бичсэн fake объект нь тухайн хамаарлын хялбаршуулсан ажиллах хэрэгжүүлэлт байдаг. Тестийн гол зорилго нь бизнес логикийг шалгах учраас тестлэгдэж буй үндсэн классыг өөрийг нь mock хийх нь тохиромжгүй. `verify()` аргыг хэт олон ашиглавал тестүүд дотоод хэрэгжүүлэлтээс хэт хамааралтай болж, логикийн үр дүн өөрчлөгдөөгүй байхад ч унах эрсдэлтэй. Иймээс буцаах утга, exception болон шаардлагатай харилцан үйлчлэлийг хослуулан шалгах нь зүйтэй гэж үзлээ. Нийт 10 тест амжилттай ажиллаж, сонгосон гурван мутаци тус бүр тестийн алдаагаар илэрсэн. Мутацийн туршилт нь тестүүд зөвхөн амжилттай ажиллаж байгаа эсэхээс гадна кодын алдааг илрүүлэх чадвартай эсэхийг үнэлэхэд хэрэгтэй болохыг ойлгосон.
