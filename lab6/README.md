## 3. A хэсэг: Category-Partition

### A1. Сонголт ба төлөөлөх утгууд

Банкны шилжүүлгийн API дараах хүсэлтийг хүлээн авна.

`POST /transfer`

Хүсэлтийн бүтэц:

```json
{
  "from": 1001,
  "to": 1002,
  "amount": 50000,
  "currency": "MNT"
}
```

Шилжүүлэг амжилттай бол HTTP `201` статус болон `{"result":"OK"}` хариу буцаана.

Алдаа гарсан тохиолдолд HTTP `200` статус болон тухайн алдааг илэрхийлэх `result` утга буцаана.

Тестийн үндсэн параметрүүдийг `From`, `To`, `Amount`, `Currency` гэж тодорхойлов.

| Параметр | Сонголт | Төлөөлөх утга | Тайлбар |
|---|---|---|---|
| From | Valid | 1001 | Хүчинтэй, царцаагдаагүй данс |
| From | Frozen | 1003 | Царцаагдсан данс |
| From | Missing | 9999 | Системд бүртгэлгүй данс |
| To | Valid | 1002 | Хүчинтэй, шилжүүлэгчээс өөр данс |
| To | Missing | 9998 | Системд бүртгэлгүй хүлээн авагч |
| To | SameAsFrom | `from`-той ижил ID | Өөрийн данс руу шилжүүлэх |
| Amount | Zero | 0 | Шилжүүлэх дүн тэг |
| Amount | Negative | -100 | Шилжүүлэх дүн сөрөг |
| Amount | Normal | 50000 MNT | Үлдэгдэл болон лимитэд багтсан дүн |
| Amount | OverBalance | 2000000 MNT | Үлдэгдлээс хэтэрсэн дүн |
| Amount | OverLimit | 1500000 MNT | Өдрийн үлдсэн лимитээс хэтэрсэн дүн |
| Currency | Same | MNT | Дансны үндсэн валют |
| Currency | Different | USD | Валют хөрвүүлэх шаардлагатай |

**Тайлбар:** Amount-ийн төлөөлөх утгууд нь MNT валюттай үндсэн жишээ юм. `Currency=Different` үед валютын ханш болон дансны үлдэгдэл, лимитэд тохируулан тусдаа дүн ашиглана.

### A2. Сонголтын хязгаарлалтууд

Category-Partition аргаар тестийн нөхцөлүүдийг тодорхойлохдоо `[ERROR]`, `[SINGLE]`, `[IF]` тэмдэглэгээг ашиглав.

- **[ERROR]** — алдаа үүсгэх сонголт.
- **[SINGLE]** — тусад нь шалгах шаардлагатай сонголт.
- **[IF]** — бусад параметрийн утгаас хамаарах хязгаарлалт.

| Параметр | Сонголт | Тэмдэглэгээ | Үндэслэл |
|---|---|---|---|
| From | Valid | Энгийн | Шилжүүлэг хийх боломжтой данс |
| From | Frozen | [ERROR] | Царцаагдсан данснаас шилжүүлэг хийх боломжгүй |
| From | Missing | [ERROR] | Шилжүүлэгч данс байхгүй |
| To | Valid | Энгийн | Хүчинтэй хүлээн авагч |
| To | Missing | [ERROR] | Хүлээн авагч данс байхгүй |
| To | SameAsFrom | [ERROR], [IF From=Valid] | Өөрийн данс руу шилжүүлэхийг хориглоно |
| Amount | Zero | [ERROR] | Дүн тэгээс их байх ёстой |
| Amount | Negative | [ERROR], [SINGLE] | Сөрөг дүнг тусгайлан шалгана |
| Amount | Normal | Энгийн | Үлдэгдэл болон лимитэд багтсан |
| Amount | OverBalance | [ERROR] | Үлдэгдэл хүрэлцэхгүй |
| Amount | OverLimit | [ERROR] | Өдрийн үлдсэн лимит хүрэлцэхгүй |
| Currency | Same | Энгийн | Валют хөрвүүлэх шаардлагагүй |
| Currency | Different | Энгийн | Хөрвүүлсэн дүнгээр үлдэгдэл, лимитийг шалгана |

#### A2.1. IF хязгаарлалтууд

**IF-1:**

`To=SameAsFrom` бол `From=Valid` байна.

Энэ нь өөрийн данс руу шилжүүлэх алдааг тусад нь шалгах үед хүчинтэй эх данс ашиглах зорилготой.

**IF-2:**

`From=Missing` үед `Amount=OverBalance` эсвэл `Amount=OverLimit` сонголтыг ашиглахгүй.

Учир нь эх данс байхгүй үед тухайн дансны үлдэгдэл болон өдрийн лимитийг шалгах боломжгүй.

Эдгээр нь тестийн загварчлалд сонгосон хязгаарлалтууд бөгөөд API-ийн бүх боломжит хүсэлтийг хориглож байгаа гэсэн үг биш юм.

#### A2.2. Хослолын тооцоо

Дөрвөн параметрийн сонголтын тоо:

| Параметр | Сонголтын тоо |
|---|---:|
| From | 3 |
| To | 3 |
| Amount | 5 |
| Currency | 2 |

Хязгаарлалтгүй нийт хослол:

**N = 3 × 3 × 5 × 2 = 90**

Python-ийн `itertools.product` ашиглан бүх хослолыг үүсгэж, хоёр IF хязгаарлалтыг шалгав.

| Үзүүлэлт | Хослолын тоо |
|---|---:|
| Хязгаарлалтгүй нийт хослол | 90 |
| IF-1 нөхцөлөөр хасагдсан | 20 |
| IF-2 нөхцөлөөр хасагдсан | 12 |
| Давхар тоологдсон хасалт | 4 |
| Хязгаарлалтын дараах хослол | 62 |

Давхардсан хасалтыг нэг удаа тооцвол:

**M = 90 − (20 + 12 − 4) = 62**

Иймээс:

**N → M = 90 → 62**

Энэ нь зөвхөн хоёр IF хязгаарлалтын дараах хослолын тоо юм. `[ERROR]` болон `[SINGLE]` тэмдэглэгээг тестийн сонголт, тусгай тестийн спецификацид ашиглана.

Тооцоог `count_combinations.py` скриптээр шалгасан.

### A3. Тестийн спецификацийн хүснэгт

Тестийн спецификацийг боловсруулахдаа амжилттай шилжүүлэг, алдааны бүх ангилал болон олон алдаа зэрэг үүссэн нөхцөлийг хамруулав.

#### A3.1. Алдааны давуу эрэмбэ

Олон алдаа зэрэг үүссэн үед дараах давуу эрэмбийг сонгов.

`ERROR_NO_FROM → ERROR_FROZEN → ERROR_NO_TO → ERROR_SAME_ACCOUNT → ERROR_BAD_AMOUNT → ERROR_INSUFFICIENT → ERROR_LIMIT`

Эхлээд шилжүүлэгч данс, дараа нь хүлээн авагч данс, эцэст нь шилжүүлгийн дүн болон лимитийг шалгана.

Энэхүү эрэмбэ нь лабораторийн тестийн oracle-д зориулан сонгосон дүрэм юм. API-ийн бодит хэрэгжүүлэлтэд алдааны давуу эрэмбэ тодорхой заагдаагүй.

#### A3.2. Тестийн спецификаци

| ID | From | To | Amount | Currency | HTTP статус | Result |
|---|---|---|---|---|---|---|
| TC01 | Valid | Valid | Normal | Same | 201 | OK |
| TC02 | Valid | Valid | Normal | Different | 201 | OK |
| TC03 | Missing | Valid | Normal | Same | 200 | ERROR_NO_FROM |
| TC04 | Frozen | Valid | Normal | Same | 200 | ERROR_FROZEN |
| TC05 | Valid | Missing | Normal | Same | 200 | ERROR_NO_TO |
| TC06 | Valid | SameAsFrom | Normal | Same | 200 | ERROR_SAME_ACCOUNT |
| TC07 | Valid | Valid | Zero | Same | 200 | ERROR_BAD_AMOUNT |
| TC08 | Valid | Valid | Negative | Same | 200 | ERROR_BAD_AMOUNT |
| TC09 | Valid | Valid | OverBalance | Same | 200 | ERROR_INSUFFICIENT |
| TC10 | Valid | Valid | OverLimit | Same | 200 | ERROR_LIMIT |
| TC11 | Frozen | Missing | Normal | Same | 200 | ERROR_FROZEN |
| TC12 | Valid | Missing | Zero | Same | 200 | ERROR_NO_TO |

TC01 болон TC02 нь амжилттай шилжүүлгийг шалгана.

TC03–TC10 нь алдааны бүх ангиллыг хамарна.

TC08 нь `[SINGLE]` тэмдэглэгээтэй сөрөг дүнгийн тусгай тест юм.

TC11 болон TC12 нь олон алдаа зэрэг үүссэн нөхцөлд давуу эрэмбийн дагуу аль алдааг буцаахыг шалгана.

#### A3.3. Тестийн орчны тодорхойлолт

Тестийн үр дүнг хоёрдмол утгагүй болгохын тулд дараах жишиг өгөгдлийг ашиглана.

| Нөхцөл | Утга |
|---|---|
| Шилжүүлэгч данс | 1001 |
| Хүлээн авагч данс | 1002 |
| Царцаагдсан данс | 1003 |
| Байхгүй шилжүүлэгч данс | 9999 |
| Байхгүй хүлээн авагч данс | 9998 |
| Дансны үндсэн валют | MNT |
| Жишиг валютын ханш | 1 USD = 3500 MNT |

Amount-ийн сонголт бүрт тохирох орчныг дараах байдлаар бэлтгэнэ.

| Amount сонголт | Шилжүүлэх дүн | Үлдэгдэл | Өдрийн үлдсэн лимит | Хүлээгдэх үр дүн |
|---|---:|---:|---:|---|
| Normal | 50000 MNT | 1000000 MNT | 1000000 MNT | OK |
| Zero | 0 MNT | 1000000 MNT | 1000000 MNT | ERROR_BAD_AMOUNT |
| Negative | -100 MNT | 1000000 MNT | 1000000 MNT | ERROR_BAD_AMOUNT |
| OverBalance | 2000000 MNT | 1000000 MNT | 3000000 MNT | ERROR_INSUFFICIENT |
| OverLimit | 1500000 MNT | 2000000 MNT | 1000000 MNT | ERROR_LIMIT |

**OverBalance:** Дансны үлдэгдэл хүрэлцэхгүй боловч өдрийн үлдсэн лимит хангалттай байна.

**OverLimit:** Дансны үлдэгдэл хангалттай боловч өдрийн үлдсэн лимит хүрэлцэхгүй байна.

**Currency=Different:** Шилжүүлгийн дүнг USD-ээр өгч, MNT-д хөрвүүлсний дараа үлдэгдэл болон лимитийг шалгана.

Жишээлбэл, TC02 тестэд:

- Шилжүүлэх дүн: 100 USD
- Хөрвүүлсэн дүн: 350000 MNT
- Дансны үлдэгдэл: 1000000 MNT
- Өдрийн үлдсэн лимит: 1000000 MNT
- Хүлээгдэх HTTP статус: 201
- Хүлээгдэх result: OK

Ингэснээр TC02 тестэд валютын хөрвүүлэлт хийгдсэн ч шилжүүлэг амжилттай болно.

Эдгээр нь бодит банкны өгөгдөл биш, тестийн зориулалтаар сонгосон жишиг утгууд юм.

## 4. B хэсэг: Microsoft PICT

### B1. Browser model

Browser тохиргооны зургаан параметрийг `browser.model` файлд тодорхойлов.

| Параметр | Сонголтууд |
|---|---|
| Content | Allow, Restrict, Block |
| Cookies | Allow, Restrict, Block |
| Popups | Yes, No |
| Addons | Yes, No |
| Attacks | Yes, No |
| Forgeries | Yes, No |

Хязгаарлалтгүй бүх хослолын тоо:

**3 × 3 × 2 × 2 × 2 × 2 = 144**

PICT хэрэгслийг дараах командуудаар ажиллуулав.

```bash
pict browser.model > results/browser-2way.txt
pict browser.model /o:3 > results/browser-3way.txt
```

Бодит үр дүн:

| Туршилт | Үүсгэсэн тест | Бүрэн хослолтой харьцуулсан хувь |
|---|---:|---:|
| 2-way | 10 | 6.94% |
| 3-way | 20 | 13.89% |
| Бүрэн хослол | 144 | 100% |

2-way арга нь параметрүүдийн боломжит хоёрлосон утгуудын хослолыг хамарна.

3-way арга нь гурван параметрийн утгуудын боломжит хослолыг хамардаг тул энэ туршилтад 2-way-ээс хоёр дахин олон тест үүсгэсэн.

### B2. Transfer model

Банкны шилжүүлгийн функцийн тестийн хослолуудыг харьцуулахын тулд дараах гурван модель боловсруулав.

- `transfer-nc.model` — IF хязгаарлалтгүй модель.
- `transfer.model` — A2 хэсэгт тодорхойлсон хоёр IF хязгаарлалттай модель.
- `transfer-neg.model` — IF хязгаарлалт болон `~` negative тэмдэглэгээ ашигласан модель.

PICT хэрэгслээр модель бүрийг ажиллуулж, үүссэн тестийн мөрүүдийг харьцуулав.

#### B2.1. Моделиудын үр дүнгийн харьцуулалт

| Модель | Боломжит бүрэн хослол | PICT тест | Happy path | 1 алдаатай | 2 алдаатай | 3 алдаатай |
|---|---:|---:|---:|---:|---:|---:|
| `transfer-nc.model` | 90 | 15 | 0 | 3 | 7 | 5 |
| `transfer.model` | 62 | 16 | 0 | 3 | 9 | 4 |
| `transfer-neg.model` | — | 18 | 2 | 16 | 0 | 0 |

**Алдааны тоог тооцсон зарчим:**

- `From=Frozen` эсвэл `Missing` бол нэг алдаатай сонголт.
- `To=Missing` эсвэл `SameAsFrom` бол нэг алдаатай сонголт.
- `Amount=Zero`, `Negative`, `OverBalance` эсвэл `OverLimit` бол нэг алдаатай сонголт.
- `Currency=Same` болон `Different` нь өөрөө алдаа биш.

Энд нэг мөр дэх алдааны тоо гэдэг нь API-ийн буцаах алдааны тоо биш, тухайн тестийн мөрд агуулагдах алдаатай сонголтын тоо юм.

**Happy path** гэдэг нь `From=Valid`, `To=Valid`, `Amount=Normal` гэсэн нөхцөлүүд зэрэг хангагдсан, амжилттай шилжүүлэг хийх боломжтой тестийн мөр юм.

Хязгаарлалтгүй `transfer-nc.model` нь 90 боломжит бүрэн хослолоос 15 pairwise тест үүсгэсэн. Эдгээрээс 3 мөр нэг алдаатай, 7 мөр хоёр алдаатай, 5 мөр гурван алдаатай байсан бөгөөд happy path үүсээгүй.

Хоёр IF хязгаарлалттай `transfer.model` нь 62 зөвшөөрөгдөх бүрэн хослолоос 16 pairwise тест үүсгэсэн. Үүнээс 3 мөр нэг алдаатай, 9 мөр хоёр алдаатай, 4 мөр гурван алдаатай байсан бөгөөд мөн happy path үүсээгүй.

Хязгаарлалт нэмэгдсэн боловч тестийн тоо 15-аас 16 болж өссөн. Учир нь IF нөхцөлүүд зөвшөөрөгдөх хослолуудыг өөрчилдөг бөгөөд PICT-ийн тест сонгох алгоритм өөр багц үүсгэж болно. Иймээс хязгаарлалттай модель заавал цөөн тест үүсгэнэ гэсэн үг биш.

Харин `transfer-neg.model` нь нийт 18 тест үүсгэсэн. Үүнээс 2 нь happy path, 16 нь нэг negative сонголттой тест байв. Хоёр болон гурван negative сонголт нэг мөрд зэрэг орсон тохиолдол гараагүй.

Эдгээр үр дүнгээс pairwise арга нь параметрүүдийн хослолыг хамруулахад үр дүнтэй боловч happy path болон бизнесийн тодорхой сценарийг заавал үүсгэдэггүй нь харагдсан. Иймээс A3 хэсэгт амжилттай шилжүүлэг болон давхар алдаатай нөхцөлүүдийг гараар боловсруулсан.

#### B2.2. Negative (`~`) тэмдэглэгээ ба IF хязгаарлалтын хамаарал

PICT-ийн `~` тэмдэглэгээ нь тухайн утгыг negative буюу алдаатай сонголт гэж тодорхойлоход ашиглагдана. Энэ тэмдэглэгээг ашигласнаар нэг тестийн мөрд олон negative сонголт зэрэг оруулахгүйгээр алдаатай нөхцөлүүдийг тусгаарлан шалгах боломжтой.

Жишээлбэл:

`Valid | Valid | ~Negative | Same`

гэсэн мөр нь хүчинтэй хоёр дансны хооронд сөрөг дүнтэй шилжүүлэг хийх нөхцөлийг илэрхийлнэ. Энэ тохиолдолд `ERROR_BAD_AMOUNT` алдааг бусад алдаанаас тусад нь шалгах боломжтой.

Харин A2 хэсгийн IF хязгаарлалтууд нь параметрүүдийн хоорондын хамаарлыг тодорхойлдог.

**IF-1:**

`To=SameAsFrom` үед `From=Valid` байна.

**IF-2:**

`From=Missing` үед `Amount=OverBalance` болон `Amount=OverLimit` сонголтыг ашиглахгүй.

Эдгээр хязгаарлалтыг тестийн утгагүй эсвэл давхардсан алдаатай хослолуудыг хасах зорилгоор тодорхойлсон.

`~` тэмдэглэгээ болон IF хязгаарлалт нь өөр өөр үүрэгтэй. `~` нь negative сонголтыг тусгаарладаг бол IF нь параметрүүдийн зөвшөөрөгдөх хамаарлыг тодорхойлдог. Иймээс **`~` тэмдэглэгээ ашигласнаар A2-ын IF хязгаарлалтууд автоматаар хэрэггүй болохгүй.**

Гэхдээ `transfer-neg.model`-д нэг мөрд хамгийн ихдээ нэг negative сонголт орох тул IF нөхцөлөөр хориглосон зарим давхар алдаатай хослол анхнаасаа үүсэхгүй.

Тухайлбал, `From=~Missing` болон `Amount=~OverBalance` нь хоёулаа negative сонголт учраас нэг мөрд зэрэг үүсэхгүй. Ийм нөхцөлд IF-2 хязгаарлалт нь тухайн гаралтад нэмэлт өөрчлөлт оруулахгүй байж болно.

Үүнтэй адил `To=~SameAsFrom` сонголт бусад negative утгуудтай зэрэг үүсэхгүй тул IF-1 нөхцөл negative тестүүдэд давхар хамгаалалтын үүрэгтэй байна.

Иймээс энэ удаагийн negative моделийн гаралтад IF хязгаарлалтуудын нөлөө хязгаарлагдмал боловч моделийн бизнесийн хамаарлыг тодорхой хадгалах, цаашид сонголтууд өөрчлөгдөхөд зөвшөөрөгдөх хослолыг хянах зорилгоор хэвээр үлдээсэн.

**Дүгнэвэл**, `transfer-neg.model` нь алдаатай сонголтуудыг тусгаарлаж, 16 negative болон 2 happy path тест үүсгэсэн. Харин A2-ын IF хязгаарлалтууд нь параметрүүдийн хамаарлыг тодорхойлох үүрэгтэй хэвээр байна.
### B3. PICT-ийн гаралтад үндэслэн боловсруулсан API тест кейсүүд

PICT-ийн гаралтаас гурван мөр сонгож, тестийн орчин, `POST /transfer` хүсэлт болон хүлээгдэх үр дүнг тодорхойлов. Сонгосон мөрүүд нь хадгалсан PICT гаралттай тохирч байгаа бөгөөд `~` тэмдэг нь PICT моделийн сөрөг сонголтыг илэрхийлнэ.

**Анхаарах зүйл:** Эдгээр нь API-ийн бодит ажиллуулалтын үр дүн биш, тестийн спецификаци юм. `PASS/FAIL` гэж дүгнээгүй; хариунуудыг хүлээгдэх үр дүн (`oracle`) болгон тодорхойлсон.

### B4. PICT-ийн greedy алгоритм

PICT нь бүх боломжит бүрэн хослолыг нэг бүрчлэн тестлэхийн оронд параметрүүдийн харилцан үйлчлэлийг хамрах цөөн тооны тест үүсгэдэг.

Pairwise буюу 2-way аргаар хоёр параметрийн утгуудын боломжит хослол бүрийг дор хаяж нэг тестэд хамруулахыг зорьдог.

Greedy алгоритм нь тухайн үед хараахан хамрагдаагүй хослолуудаас аль болох олныг хамруулах тестийг сонгох зарчимтай.

Ингэснээр нэг тест хэд хэдэн шинэ хослолыг зэрэг хамарч, нийт тестийн тоог багасгах боломжтой.

Гэхдээ greedy арга нь хамгийн цөөн тесттэй оновчтой шийдлийг заавал баталгаажуулахгүй. Pairwise хамралт нь бизнес дүрмийн бүх боломжит сценарийг дангаараа баталгаажуулахгүй учраас амжилттай болон давхар алдаатай нөхцөлүүдийг гараар нэмж тодорхойлсон.

Энэ лабораторид Browser-ийн 144 бүрэн хослолыг 2-way аргаар 10, 3-way аргаар 20 тестээр төлөөлүүлсэн.

Мөн Transfer-ийн 90 бүрэн хослолтой хязгаарлалтгүй моделийг 15 тестээр төлөөлүүлсэн.

## 5. Дүгнэлт

Энэхүү лабораторийн ажлаар Category-Partition аргаар банкны шилжүүлгийн функцийн тестийн нөхцөл, сонголт болон хязгаарлалтыг тодорхойлсон. Гараар боловсруулсан тестийн спецификацид амжилттай шилжүүлэг, алдааны бүх ангилал болон олон алдаа зэрэг үүссэн нөхцөлийг хамруулсан. Дөрвөн параметрийн нийт 90 хослолыг Python ашиглан тооцож, хоёр IF хязгаарлалтын дараа 62 хослол үлдэж байгааг баталгаажуулсан. PICT хэрэгслээр Browser-ийн 2-way тестэд 10, 3-way тестэд 20 мөр үүссэн. Transfer-ийн хязгаарлалтгүй модель 15, хязгаарлалттай модель 16 тест үүсгэсэн нь хязгаарлалт нэмэхэд тестийн тоо заавал буурдаггүйг харуулсан. Negative модельд 18 тест үүссэн бөгөөд алдаатай сонголтуудыг тусгаарлан шалгах боломж бүрдсэн. PICT-ийн гаралтаас гурван мөр сонгон, бодит хүсэлтийн өгөгдөл болон хүлээгдэх хариуг тодорхойлсон. Гараар боловсруулсан тестүүд нь бизнес дүрэм болон алдааны давуу эрэмбийг шалгахад, PICT нь параметрүүдийн хослолын хамрах хүрээг нэмэгдүүлэхэд илүү тохиромжтой байсан. Иймээс хоёр аргыг хамтад нь ашиглах нь тестийн тоог зохистой хэмжээнд хадгалж, шалгалтын хамрах хүрээг сайжруулах боломжтой гэж дүгнэсэн.
